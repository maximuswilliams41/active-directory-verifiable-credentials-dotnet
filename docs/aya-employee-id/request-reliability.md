## Changes and defensive review

- `IAyaRequestPersistence` separates atomic persistence from the existing request-state service. There is no runtime memory fallback. An unset backend or persistence failure prevents new service requests and yields a sanitized unavailable response.
- The file adapter reads a fresh versioned, checksummed snapshot for each transaction; it flushes a replacement file before same-directory atomic replacement. A lifetime exclusive file handle enforces one writer. Missing previously initialized state, corrupt/unsupported snapshots and failed writes fail closed. The checksum detects accidental corruption, not malicious administrator modification; access control remains mandatory.
- Creation persists pending ownership (tenant plus object ID), kind and expected issuer before contacting Request Service. Authenticated early callbacks are stored as minimal events and do not become success until the returned service request ID matches. Service timeouts, invalid responses and unreconciled callbacks remain uncertain; there is no automatic repeat of the issuance POST.
- Pending submission has a ten-minute limit. A validated service response must have a future expiry at most ten minutes away. Its QR expiry and two-minute callback grace are separate from a fixed 24-hour result visibility window measured from local creation. Duplicates extend neither deadline. Unknown and conflicting events cannot overwrite terminal outcomes. A crash after remote acceptance but before local response binding remains an explicitly unconfirmed outcome requiring owner review; this is not an exactly-once issuance guarantee.
- Unexpired nonterminal requests prevent a second active request of the same kind for the same owner. Expired records become unavailable at retention expiry and are physically pruned on the next creation. The pilot owner must remove the journal at teardown if no later creation occurs. Capacity is limited to 2,000 records and 4 MiB; capacity failures do not fall back to volatile state.
- Issuance and presentation callbacks share configured authentication, body/depth limits, request-kind/state/service-ID correlation and durable acknowledgement. Callback origin is explicit configuration, not a browser-provided host. Result polling is authenticated, owner-bound and no-store, with distinct routes for issuance and presentation.
- The verifier now creates an antiforgery-protected POST through the mocked-capable token provider. It requests only `AyaEmployeeId` from the configured Aya DID, with linked-domain validation, revocation checking and no receipt. Query/template overrides, Face Check and selfie operations are unavailable for this pilot. Existing helper signatures remain non-actions and cannot relax the Aya policy.
- Presentation success requires one credential with the expected issuer/type, explicit `VALID` status, future expiration and all four minimum claims with a canonical employee key. Expiration is checked again on polling. Only sanitized status is persisted/returned; names, employee numbers, key claims, raw receipts, PINs, tokens and callback bodies are not journaled.
- The existing employee experience is retained. Both flows hide expired QR links, allow a bounded final-result window, and distinguish unconfirmed outcomes from success. Browser refresh does not restore QR/PIN secrets; an existing browser can continue status polling through an application restart. Authenticator/card appearance is not employment proof, and automated offboarding remains a separate mocked milestone.

## Storage decision before deployment

The current application uses managed-identity Azure Table Storage. Follow the [atomicity design and owner-only resource checklist](table-request-storage.md). The built-in Linux App Service `/home` mount is no longer used for request-state persistence, and setting `Aya:RequestStorePath` has no runtime effect. No Table resources or permissions are created automatically. Deployment and activation remain separate owner approvals.
